# LAN-462 어드민 전체 푸시 캠페인 및 테스트 발송 구현

## 배경

관리자가 서비스 공지를 앱 푸시로 전달할 수 있도록 전체 발송 기능을 제공한다. 기존 예약 학습 알림의 일일 정책과 상태는 유지하고, 캠페인 단위로 발송 대상과 결과를 추적한다.

상세 구현 계약은 [설계 문서](design.md)를 기준으로 한다. 현재 문서는 구현 전 이슈 초안이며, 설계 승인·구현 완료·운영 발송을 의미하지 않는다.

## 요구사항

### 캠페인과 관리자 권한

- 관리자는 제목·내용·딥 링크를 입력해 캠페인을 생성하고 목록·상세를 조회할 수 있다.
- 캠페인 내용은 생성 즉시 변경할 수 없다. 내용 변경은 새 캠페인 생성으로 처리한다.
- 캠페인별 전체 발송 실행은 하나만 생성한다. 서로 다른 캠페인은 같은 날에도 발송할 수 있다.
- 모든 관리 API는 관리자 권한을 검사한다.
- 생성·테스트 발송·전체 발송·중단된 실행 복구는 관리자 감사 로그에 기록한다.

### 대상과 예상 수

- 발송 단위는 사용자 계정이 아닌 활성 Expo Push Token이다. 다기기 사용자는 기기마다 알림을 받을 수 있다.
- 후보는 `ACTIVE` 사용자에 속한 `ACTIVE` 토큰이다. 학습 상태나 예약 알림 선정 조건을 적용하지 않는다.
- 전체 발송 전에 예상 사용자 수·토큰 수·조회 시각을 확인할 수 있다. 예상 수는 실제 확정 수와 다를 수 있다.
- 비동기 준비 단계에서 실제 대상 목록을 한 번 확정·저장한다. 확정 후 신규 토큰은 추가하지 않는다.
- 발송 직전 사용자·토큰 활성 상태, 토큰 소유자와 문자열을 재검증하고 변경된 대상은 제외한다.
- 재처리는 최초 확정한 목록을 사용한다.

### 관리자 테스트

- 관리자는 전체 발송 시작 전에 인증된 본인의 활성 토큰에 캠페인의 동일한 제목·내용·딥 링크로 테스트할 수 있다.
- 임의 사용자나 토큰을 테스트 대상으로 지정할 수 없다.
- 테스트 실행은 별도 ID·중복 키·집계를 사용한다. 테스트를 받은 토큰도 이후 본 발송을 받을 수 있다.
- 같은 요청 키의 테스트 재요청은 기존 실행을 반환하며, 새 요청 키로 재테스트할 수 있다.
- 관리자별 새 테스트 요청은 10초에 한 번으로 제한하고, 활성 토큰이 없으면 실행 결과에 이를 표시한다.

### 비동기 처리와 중복 방지

- API는 실행을 DB에 저장하고 `202 Accepted`를 반환한다. DB에 남은 작업을 SQS로 발행하고 기존 BE Push 소비 흐름에서 처리한다.
- 기존 발송 이력·Ticket·Receipt·Expo 최대 100건 배치를 재사용한다. 확정 대상은 Keyset 페이지로 읽는다.
- 전체 발송 키는 `push:admin-broadcast:{campaignId}:{userPushTokenId}`를 사용한다.
- 관리자 테스트 키는 `push:admin-broadcast-test:{runId}:{userPushTokenId}`를 사용한다.
- API 요청 키·DB 유일 제약·원자적 발송 선점으로 중복 요청과 SQS 재처리를 처리한다. 전체 발송은 다른 키로 다시 요청해도 기존 실행을 반환한다.
- Expo 접수 여부가 불명확한 타임아웃·통신 오류·프로세스 종료는 자동 재발송하지 않고 `UNKNOWN`으로 기록한다. 중복 방지를 우선하므로 일부 누락이 발생할 수 있다.
- 명시적인 HTTP 429 거부만 제한적으로 재시도한다. 이미 접수한 알림은 Receipt만 재조회한다.
- SQS 발행 실패·진행 중 종료·Receipt 예약 유실에서 같은 실행을 복구한다. 반복 작업 장애는 `BLOCKED`로 표시하고 관리자는 미처리 작업을 재개할 수 있다.
- Expo·APNs·FCM·OS의 중복 표시 및 실제 기기 도착은 정확히 한 번 보장하지 않는다.

### 예약 학습 알림과 독립성

- 공지 발송으로 `user_notification_state`와 예약 알림의 일일 중복 키를 변경하지 않는다.
- 같은 날 공지와 20시 예약 학습 알림을 각각 발송할 수 있다.
- 유효하지 않은 토큰은 기존 정책대로 비활성화한다. 해당 토큰이 이후 예약 알림에서 제외되는 것은 정상 동작이다.
- 공지는 한 메시지당 최대 100토큰을 처리하고, 인스턴스 전체에서 동시 제출 배치 1개·초당 최대 100토큰으로 제한한다.
- 공유 SQS·Expo 자원에 따른 처리 지연은 별도로 측정하며, 예약 알림의 지연이 전혀 없다는 보장은 포함하지 않는다.

### 입력과 딥 링크

- 앞뒤 공백 제거 후 제목·내용·딥 링크는 필수이며 최대 길이는 각각 255·500·1,000자다.
- 한글·이모지를 포함한 직렬화된 표시 payload는 자체 기준 3,000바이트 이하로 검증한다.
- 내부 경로는 단일 `/`로 시작하는 유효한 앱 경로를 허용한다. `//host`·역슬래시·제어문자·잘못된 인코딩은 거부한다.
- 외부 링크는 유효한 DNS 호스트, 사용자 인증정보 없음, 기본 포트 또는 443인 HTTPS URL을 허용한다. v1에 도메인 목록 제한은 없다.
- `http`·`javascript`·`file`·`intent` 등 허용하지 않는 스킴과 잘못된 URL은 서버에서 거부한다.
- 기존 `data.url` 계약을 사용한다. FE는 내부 경로를 앱에서, 외부 HTTPS를 시스템 브라우저에서 연다.
- 미지원 내부 경로는 `/home`으로 이동하고, 인증 필요 화면은 로그인 후 이동한다. 앱 종료 상태와 구버전 호환을 FE 핸드오프에서 확인한다.

### 상태와 결과

- 캠페인 전체 실행과 테스트 실행의 상태·집계를 구분해 조회한다.
- 상태는 대기·대상 준비·발송 중·Receipt 대기·완료·진행 중단을 구분한다.
- 확정 사용자 수·토큰 수와 처리 중·성공·실패·제외·확인 불가 토큰 수를 제공한다.
- 성공은 Receipt의 APNs/FCM 인계 성공이다. 실제 기기 표시·사용자 열람 성공을 의미하지 않는다.
- `확정 토큰 수 = 처리 중 + 성공 + 실패 + 제외 + 확인 불가`가 유지돼야 한다.
- 테스트·중복 재처리로 전체 발송 집계가 증가하지 않는다. 완료 상태도 실패·확인 불가 결과를 포함할 수 있다.

- [ ] 관리자 본인 대상 테스트 발송 및 요청 멱등성·빈 대상 처리를 구현한다.
- [ ] 예상 대상 수 조회와 실제 대상의 원자적 스냅샷 저장을 구현한다.
- [ ] 캠페인·실행·대상 테이블과 기존 발송 이력 연결을 Flyway로 추가한다.

- [ ] 토큰 단위 키·유일 제약·선점으로 동시 API 요청과 SQS 중복 처리를 검증한다.
- [ ] 토큰 소유자 변경·비활성화·확정 후 신규 등록에 대한 정책을 검증한다.
- [ ] 결과 불명 시 재발송 금지, 제한된 429 재시도, Receipt만 재조회하는 정책을 검증한다.
- [ ] SQS 발행 실패·응답 유실·선점 후 종료·Receipt 예약 유실·DLQ 및 중단 복구를 검증한다.
- [ ] 테스트 후 본 발송, 같은 날 여러 캠페인과 예약 알림의 독립성을 검증한다.
- [ ] 공지 전후 `user_notification_state`가 동일함을 검증한다.
- [ ] 상태·집계 등식·오류 사유와 감사 로그를 검증한다.
- [ ] 다중 인스턴스 공지 제한과 대상·집계 조회 성능, 공유 큐 지연을 확인한다.
- [ ] PostgreSQL에서 마이그레이션·유일 제약·잠금·스냅샷·동시성 계약을 검증한다.
- [ ] 관련 단위·통합 테스트와 `./gradlew check`가 통과한다.
- [ ] 인증·동시성·마이그레이션·공통 발송 변경에 대한 독립 리뷰를 완료한다.
- [ ] OpenAPI와 어드민·앱 FE·운영 복구 핸드오프를 반영한다.
- [ ] 승인된 관리자 테스트에서 실제 기기 알림과 내부·외부 딥 링크 이동을 확인한다.

## 작업 메모

- 상세 상태 전이·API·데이터 모델·실패 처리는 설계 문서를 단일 기준으로 사용한다.
- 새 알림 유형은 `ADMIN_BROADCAST`, `ADMIN_BROADCAST_TEST`다.
- 기존 학습 대상 조회 전체를 재사용하지 않고, 필요한 사용자·토큰만 조회한다.
- 기존 예약·편지함 알림의 재시도 정책을 공지 정책에 맞춰 일괄 변경하지 않는다.
- 새 캠페인 생성은 같은 내용이라도 별도 발송이다. 일부 장애 복구에는 같은 실행의 재개 기능을 사용한다.
- 운영 DB 적용·데이터 수동 수정·실제 운영 테스트 및 전체 발송은 별도 승인 후 진행한다.
- FE 지원과 구버전 동작이 확인되기 전 외부 URL을 운영 발송에 사용하지 않는다.
