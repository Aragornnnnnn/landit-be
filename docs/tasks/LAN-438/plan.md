# LAN-438 공통 온보딩 진단 4문항

## 확정 계약

- 시나리오 1 신규 시작은 사용자 수준 미설정 또는 1~5 모두 같은 4문항이다.
- 질문과 번역 원문은 onboarding-questions.json을 기준으로 한다.
- 질문 묶음 DIAGNOSTIC은 사용자 수준이 아니다. 최초 수준 평가는 1~5 전체 범위다.
- 신규 시작과 목록·일일·관리자 미리보기는 공통 진단 묶음을 사용한다.
- 과거 세션은 저장된 질문 그룹과 3문항 구성을 유지한다. 기존 질문·번역·메타데이터·음원을 덮어쓰거나 비활성화하지 않는다.
- 4문항의 실제 답변 모두 평가하며 기존 Core/Details, 충분성, 초기화·승급·Fallback 계약을 유지한다.
- 사용자 수준 선택 화면 삭제는 FE 작업이다. 기존 사용자 설정 API 삭제는 포함하지 않는다.

## 구현과 검증

- 공통 그룹 CHECK 제약 추가, 신규 시작과 미리보기 조회 변경.
- 기존 세션 후속 질문과 평가 메타데이터는 저장된 그룹으로 조회.
- 수준 미설정 및 1~5 각각 4문항 진행·마지막 턴 완료·평가 입력 4건 통합 테스트.
- 진단 그룹의 Level 1~5 평가 범위 및 기존 그룹 질문 보존 회귀 테스트.
- 독립 검수에서 기존 그룹 덮어쓰기 위험을 발견해 별도 DIAGNOSTIC 그룹으로 보완.
- 최종 `./gradlew spotlessApply check` 통과. 실제 V87 SQL 실행, 수준 미설정·1~5의 공통 질문 진행, 기존 세션 질문 수 3 보존을 검증했다.
- V86/V87, 질문·번역·메타데이터·음원 URL까지 포함한 독립 재검수에서 추가 blocker 없음.

### 블라인드 기준표 작성

1. 작성과 분리된 새 컨텍스트에서 기준 평가를 수행한다. 입력은 공통 질문·답변과 고정 루브릭뿐이며, 작성 목표 수준과 제품 평가 결과를 보여주지 않는다.
2. 기준표에는 질문별 5개 영역의 수준 또는 미관찰 상태, 원문 근거, 세션별 허용 수준 범위, 수준 확정 가능 여부를 기록한다. 자료만으로 판단할 수 없는 항목은 억지 정답을 만들지 않는다.
3. 가능하면 제품 평가 모델과 다른 모델로 기준표를 만든다. 사람 검수 전에는 model_reference라는 출처를 명시하고, 정확도가 아닌 기준 평가와의 일치도로 보고한다. 기존 사용자 자가선택 수준도 정답으로 취급하지 않는다.
4. 입력 파일과 기준표를 별도 파일로 저장하고 해시·분할을 봉인한다. 실행기는 입력만 읽고, 결과 생성이 끝난 뒤 별도 채점기가 기준표와 결합한다.
5. 질문별 기준표를 실제 BE 계산에 넣어 정책 기대값도 만든다. 독립 세션 수준 판단과 BE 정책 기대값은 분리해, LLM 판정 오차와 가중 계산·충분성 정책의 한계를 구분한다.

### 실제 실행 순서

1. 로컬 API와 격리 DB를 준비하고 2개 대화로 연결만 점검한다. 사용자 learningLevel=null, promotionStreak=0이며 시나리오 진행 가능 상태여야 한다. 관리자 세션도 진행도를 쓰므로 반복마다 독립 사용자를 쓴다.
2. 실제 BE 경로로 시나리오 1 세션 시작 → TEXT 답변 4회 제출 → 턴별 피드백 준비 → 세션 피드백 POST → DB·프로필 확인 → 표현 GET을 실행한다. API 계약의 실제 DTO와 기존 ScenarioSessionApiIntegrationTests를 재사용한다.
3. AI의 session-feedback은 같은 프로세스에 쌓인 message-feedback 캐시와 원문 일치 검사가 필요하다. 단일 AI 프로세스에서 정상 턴 처리를 완료하고, 최종 평가만 단독 호출하거나 캐시를 가짜 값으로 채우지 않는다. API가 반환한 실제 질문·ID·완료 상태를 사용한다.
4. 40개 대화를 각각 1회 실행한다. 반복성 표본은 출력 확인 전에 기본 대화 중 수준별 2개씩 10개를 고정하고, 각 2회 추가 실행한다. 총 60개 신규 세션이다. 반복은 새 사용자·세션으로 전체 대화를 다시 수행한다.
5. 최초 2개 연결 점검에서 endpoint별 호출 수·재시도·토큰·비용·시간을 기록하고 전체 비용을 추정한다. 세션 평가 60회가 전체 LLM 호출 60회를 뜻하지 않는다. 상한 없는 재시도는 하지 않으며 테스트 실패도 결과로 보존한다.
6. 봉인 검증용 데이터 실행 중 기준표·평가 로직을 수정하지 않는다. 실패 원인을 관찰/근거 검증/JSON 복구/충분성/수준 적용/표현 조회로 분류한다. 개선 실험은 baseline 이후 별도 run과 신규 holdout으로 수행한다.

### 필수 관찰과 오류 테스트

- DIAGNOSTIC 4문항, 4번째 답변에서 완료, AI 평가 입력 4개, 저장된 Core의 ID·원문 근거 일치를 확인한다.
- 응답 source, 각 영역 score/confidence/observedCount, sufficientEvidence, assessedLevel, displayLevel, changeType, previous/appliedLevel 및 프로필 실제 값을 기록한다. displayLevel의 기본값을 평가 성공으로 세지 않는다.
- 각 영역의 요구도 총합은 3.4다. MEDIUM 1개 미관찰이면 2.7/3.4≈0.79, HIGH 1개 미관찰이면 2.4/3.4≈0.71이다. 해당 영역 외에는 동일한 fixture로 충분성 통과·실패 차이를 확인한다.
- 5개 영역 모두 충분해야 INITIALIZED다. 짧은 적절한 답변이 불필요하게 미관찰로 처리되는지, 상호작용·화용 근거 부족으로 대부분 NOT_APPLIED가 되는지 별도로 집계한다.
- 실제 4문항에서 Level 5의 상황 수행·화용 근거를 관찰할 기회가 있는지 확인한다. 고급 기준 대화가 낮게 나와도 즉시 모델 오답으로 단정하지 않고 질문 관찰 기회와 루브릭의 한계를 함께 분석한다.
- 모델 응답 토큰 제한은 현재 평가 포함 시 2048이다. 응답 잘림·형식 오류·Core 유실을 따로 기록한다. 이를 테스트 도중 임의로 늘리지 않는다.
- 오류 주입은 별도 로컬 stub 회귀 검사로 수행한다: Details만 오류, Core 오류, timeout, AI 5xx, 캐시 원문 불일치. 실제 네트워크 품질 결과와 합산하지 않는다.
- 오류에도 BE 결과 응답이 유지되는지, 무효 평가가 프로필·streak를 바꾸지 않는지, 같은 세션 피드백 재요청이 평가 행·수준 변경을 중복 생성하지 않는지 확인한다. AI의 직접 응답은 오류일 수 있으므로 항상 응답 계약은 BE에서 검증한다.
- 피드백 응답 완료 후 GET /api/v1/expressions/1을 호출해 현재 적용 수준의 난이도와 일치하는지 확인한다. 진단 실패 시 미설정 프로필은 유지되고 기존 기본 난이도 4~5가 나오는 현행 동작은 미결 정책으로 보고한다.

| 정상 기준 대화의 최초 수준 확정 | 기준 평가가 확정 가능하다고 판정한 대화 중 90% 이상. 성공/전체 n을 함께 표시한다. |
| 기준 수준 일치 | 확정 가능 대화에서 허용 범위 내 80% 이상, 범위로부터 1단계 이내 95% 이상. 미확정은 실패로 포함하고 확정 건만의 일치율도 별도 제공한다. |
| 반복성 | 반복 표본 10개에서 3회 assessedLevel 범위가 1 이하이고 INITIALIZED 여부가 동일. 미확정 횟수도 표시한다. |
| 영역 평가 | 5개 영역별 차이·미관찰율·판정자 불일치를 보고한다. 종합 점수 하나로 숨기지 않는다. |
| 데이터·적용 불변조건 | 잘못된 근거 수용, invalid/Fallback의 프로필 변경, 중복 평가·수준 변경 0건. 오류 주입 시 BE 응답 100%. |
| 운영 참고값 | 실제 호출 기준 형식 오류율·Fallback율·토큰·비용·p50/p95 지연. 표본 수와 재시도 포함 여부를 명시한다. |

- 봉인 검증용 20개 결과를 주 결과로 보고하고 개발용·경계·반복·오류 주입 결과는 각각 분리한다. 모든 비율에 분모를 적는다.
- 결과물: 익명 입력, 별도 기준표, 실행 manifest(HEAD·모델·설정·해시), 세션별 결과 JSONL, 요약 보고서, 실패 사례별 원문과 판단 근거.
- 합성 데이터만 저장하며 시크릿·인증 헤더를 결과에 포함하지 않는다. 결과 디렉터리는 실행 시 별도로 정하고 대용량 원시 산출물은 자동 커밋하지 않는다.
- 최종 보고서는 수준 구분 가능 여부, 초기화 차단 비율, 가장 큰 실패 원인 3개, 수정이 필요한 최소 범위, 사람/실사용자 검증이 남은 항목을 명시한다.

## 비동기 수준 평가·JSON 호환 처리 수정 계획

상태: **2026-09-07 KST 구현 완료.** 이 문서의 날짜는 Asia/Seoul 기준이다(UTC 2026-09-06 늦은 오후는 KST 다음 날). 위 baseline 실행 기록은 당시 구조를 설명하며, 아래 계약을 AI·BE 코드와 통합 테스트에 반영했다.

### 1. 목표와 변경 경계

- 시나리오 완료 직후 수준 평가를 시작하고, FE는 피드백을 보여주는 동안 상태를 폴링한다.
- 사용자 확정: 기존 BE 피드백 API는 수준 평가 도입 전 응답 구조를 유지한다. 수준 평가 결과와 처리 상태는 신규 수준 평가 GET API에서만 반환한다.
- 평가 기준은 유지한다: 질문별 5영역 평가 → 요구도 가중 평균 → 영역 가중치 → 상한 보정, 충분성, 최초 초기화, 2회 승급, 자동 강등 없음.
- 제품 평가 모델·루브릭·가중치·임계값을 실행 모델의 판단으로 바꾸지 않는다. 호출 분리에 필요한 입출력 지시문만 조정하고 변경점을 기록한다.
- JSON 출력 방식 전환은 **별도 JSON_schema 이슈의 공통 구현**을 재사용한다. LAN-438에서 다른 API까지 중복 구현하지 않는다.
- 이번 인계는 AI·BE 수정과 FE 계약이다. FE 구현 완료, 운영 DB 적용, 배포, 실제 결제 검증은 포함하지 않는다.

### 2. 현재 코드에서 분리할 지점

| 현재 구조 | 수정 방향 |
| --- | --- |
| AI `generate_session_feedback`가 요약과 수준 평가를 함께 생성한다. | 기존 요약 요청과 독립 수준 평가 요청을 분리한다. |
| AI는 피드백 반환 후 메시지 캐시를 삭제하며, 평가가 이 캐시의 원문과 비교한다. | 새 수준 평가 API는 BE에 저장된 질문·답변·메타데이터를 받는다. 캐시 유무나 요약 호출 순서에 의존하지 않는다. |
| BE `SessionFeedbackService.getOrCreate`는 AI 결과를 기다린다. | 기존 피드백 API는 요약·턴 피드백만 기다린다. 수준 평가 완료는 기다리지 않는다. |
| `SessionFeedbackCompletionService.record`가 요약·평가·진행도를 함께 저장한다. | 요약·진행도 저장과 평가·사용자 수준 저장을 분리한다. 각 흐름의 멱등성을 유지한다. |
| 요약만 있고 평가가 없으면 `attachLegacyFallback`이 평가를 확정한다. | 피드백 조회 경로에서 평가 보완을 제거한다. 평가 예약·이력이 없는 과거 세션은 신규 GET에서 NOT_REQUESTED로 반환하고, PREPARING을 임의 fallback으로 확정하지 않는다. |
| `responseFor`가 평가 존재와 source에 의존해 피드백 응답을 조립한다. | 평가 조회·필수 존재 조건을 제거한다. 메시지 피드백 정합성 검증은 평가 source가 아닌 요약·피드백 자체의 생성 결과를 기준으로 유지한다. |
| `SessionMessageSubmitService`의 완료 저장 이후에도 예외 보상 코드가 실행될 수 있다. | 평가 dispatch 실패를 기존 발화 삭제 보상 경로에 흘리지 않는다. 완료 커밋 뒤 별도 처리한다. |

이 분리로 피드백 조회가 즉시 반환된다는 뜻은 아니다. 기존 요약 생성과 턴 피드백 준비 시간은 남지만 **수준 평가 지연이 피드백 화면을 막지는 않는다.**

### 3. 목표 흐름과 API

```text
마지막 답변·세션 완료·평가 PREPARING을 DB에 커밋
  ├─ BE → AI 수준 평가 → 검증·계산 → 평가/사용자 수준/COMPLETED 동시 저장
  └─ FE → 기존 피드백 POST → 요약·턴 피드백 표시
           └─ 수준 평가 GET 폴링 → 결과 표시 → 최신 수준의 표현 학습 조회
```

| 계약 | 계획 |
| --- | --- |
| AI 신규 `POST /api/v1/conversation/session-level-assessment` | `sessionId`, `scenario`, `expectedMessageIds`, `assessmentMessages`를 입력받고 `sessionId`, `levelAssessment`를 반환한다. Core 복구 소진 시 평가는 null이다. |
| AI 기존 `POST /api/v1/conversation/session-feedback` | 새 BE 흐름에서는 assessmentMessages를 보내지 않는다. 기존 결합 요청 계약은 전환 기간 동안 유지한다. |
| BE 신규 `GET /api/v1/sessions/{sessionId}/level-assessment` | `sessionId`, `processingStatus`, `levelAssessment`를 반환한다. 소유권 확인 후 저장된 상태를 조회한다. LLM 호출을 시작하거나 재생성하지 않는다. |
| BE 기존 `POST /api/v1/sessions/{sessionId}/feedback` | 수준 평가 도입 전 구조인 `sessionId`, `nativeScore`, `starRating`, `highlightMessage`, `summaryMessage`, `messageFeedbacks`만 반환한다. LAN-438의 `levelAssessment` 필드를 제거하고 평가 상태 필드도 추가하지 않는다. |
| BE 마지막 발화 응답 | 수준 평가를 기다리지 않고 기존 세션 완료 정보를 응답한다. 별도 평가 상태 필드를 추가하지 않으며, FE는 세션 완료를 기준으로 신규 GET을 시작한다. |

- 새 AI 요청 DTO는 기존 `SessionAssessmentMessage`와 Core/Details 타입을 재사용한다. 빈 입력, 중복·누락·순서 불일치 ID를 거부한다.
- BE가 저장된 소유 세션의 실제 원문과 질문 스냅샷으로 입력을 구성한다. FE가 보낸 임의 평가 입력은 신뢰하지 않는다.
- AI는 요청 원문에서 근거의 연속 부분 문자열 여부를 검사하고, BE는 저장 원문에 대해 다시 검증한다. 기존 캐시 비교를 없애는 대신 검증 근거를 DB 스냅샷으로 옮긴다.
- 피드백 POST는 평가 상태와 관계없이 같은 응답 구조를 유지한다. 신규 GET만 `processingStatus`와 nullable `levelAssessment`를 사용한다. 기존에 저장한 평가는 삭제하지 않고 신규 GET으로 조회한다.
- 전환 순서는 AI의 신규 API 제공 → BE 분리 계약 제공 → FE 폴링 연결이다. 배포 실행 승인은 별도다. 구현 전에 LAN-438의 실제 배포 여부와 FE가 피드백 내 `levelAssessment`에 의존하는지 확인하고 해당 소비부를 신규 GET으로 옮긴다. 이미 배포된 소비부가 있으면 호환 전환 순서를 먼저 맞춘다.
- 기존 결합 경로와 신규 독립 경로가 같은 세션을 각각 평가하지 않도록 요청별 평가 소유 경로를 하나로 고정한다.

### 4. 상태·저장·실패 계약

| processingStatus | levelAssessment | 처리 |
| --- | --- | --- |
| NOT_REQUESTED | null | 평가를 예약하지 않은 진행 중·과거 세션이다. 조회만으로 과거 평가를 새로 시작하지 않는다. |
| PREPARING | null | 평가 중이다. 숫자나 FALLBACK 평가 행을 미리 만들지 않는다. |
| COMPLETED | source=MODEL 또는 FALLBACK | 평가 결과 저장이 끝났다. 유효 Core라도 근거 부족이면 MODEL·NOT_APPLIED일 수 있다. |
| FAILED | null | 결과 저장 등 인프라 실패로 정상적인 결과 확정이 불가능하다. LLM 오류의 일반 종착점으로 쓰지 않는다. |

- 작업 상태는 `learning_session`에 nullable `level_assessment_processing_status`, `level_assessment_requested_at`을 추가한다. null은 API의 NOT_REQUESTED로 매핑한다. 완료 평가가 이미 있으면 COMPLETED로 응답한다.
- `user_level_assessment`는 기존처럼 **확정된 결과만** 저장한다. Core/Details JSON과 영역별 점수 저장 구조를 대기 상태를 위해 완화하지 않는다. 새 평가/작업 테이블은 만들지 않는다.
- 평가 결과·프로필의 적용 수준/streak·처리 완료 상태를 한 트랜잭션에서 저장한다. 기존 세션별 평가 unique 제약과 행 잠금을 유지한다.
- 같은 세션의 예약을 원자적으로 한 번만 허용한다. 외부 호출은 트랜잭션 밖에서 수행하며, 저장 시 PREPARING인지 재확인한다. 요약 저장도 별도로 기존 멱등성을 유지한다.
- 잠금 순서는 사용자 → 세션으로 통일한다. 이미 terminal 상태면 늦은 모델 응답은 폐기하며 프로필·streak를 바꾸지 않는다.
- 서로 다른 세션의 평가가 역순 완료되면 이전 세션 결과는 이력에 저장하되 NOT_APPLIED로 처리한다. 비교 기준은 세션 완료 시각과 ID다. 더 최신 결과의 수준·streak를 과거 결과로 덮어쓰지 않는다.
- `user_profile.learning_level_updated_at`이 평가 예약 이후이면 NOT_APPLIED로 저장한다. 수준·승급 상태 변경만 이 시각을 갱신하며 억양·푸시 등 프로필 수정은 평가를 막지 않는다. 수동 변경과 평가 저장은 사용자 잠금으로 직렬화한다. V89로 nullable 시각을 추가한다.
- 요약 실패가 유효한 수준 평가를 버리거나, 수준 평가 실패가 요약·진행도 저장을 막지 않게 한다. 두 저장 순서를 모두 테스트한다.

### 5. 비동기 실행과 대기 상한

- 배포 설정 계약: AI `SESSION_LEVEL_ASSESSMENT_BUDGET_SECONDS`(기본 100초) < BE `LANDIT_AI_SESSION_FEEDBACK_REQUEST_TIMEOUT`(기본 120초), AI 예산 < PREPARING 만료 120초. BE timeout을 낮추면 AI 예산도 함께 낮추고 전송·저장 여유를 둔다.
- 예약 시각은 세션 완료 시각을 재사용하며, 만료 판정도 동일한 주입 Clock을 사용한다.
- 수동 수준 변경과 평가 수준 반영 시각도 같은 Clock에서 생성하여 전달한다. 서버 기본 시간대와 무관하게 늦은 평가가 수동 변경을 덮어쓰지 않게 한다.
- 미배포 V88의 상태 CHECK는 `NOT VALID`로 추가하여 기존 행 검사 중 쓰기 차단을 피한다. 신규·수정 행에는 즉시 적용된다. 후속 저트래픽 운영 작업에서 별도 신규 migration으로 `ALTER TABLE learning_session VALIDATE CONSTRAINT chk_learning_session_level_assessment_processing_status;`를 실행한다. 이번 배포에서 즉시 검증하지 않는다.
- V88은 기존 vendor migration 방식으로 PostgreSQL/H2를 분리했다. H2는 `NOT VALID`를 지원하지 않아 일반 CHECK를 사용한다.

- 완료 트랜잭션에 PREPARING을 기록하고 커밋 뒤 dispatch한다. 중도 종료·미완료 세션과 과거 히스토리 조회는 진단 트리거가 아니다.
- **사용자 확정: V1은 속마음과 같은 서버 내부 비동기 방식으로 기존 `applicationTaskExecutor`를 재사용한다.** SQS, 별도 Worker, 새 실행기·범용 작업 프레임워크를 추가하지 않는다. LAN-438 V1에 한정한 아키텍처 원칙의 예외이며 실행기 선택을 다시 승인받지 않는다.
- 서버 재시작 후 작업 재실행은 보장하지 않는다. DB의 PREPARING을 보존하고 만료 후 조회 시 결정적 fallback으로 종료한다. FE가 이탈한 경우 다음 조회에서 만료를 정리하며, 별도 복구 스케줄러·무제한 자동 재시작·새 작업 큐는 추가하지 않는다.
- V1은 기존 `sessionFeedbackRequestTimeout`을 수준 평가 AI 호출에도 재사용하고, `PREPARING` 만료는 120초로 둔다. 기존 다른 endpoint의 timeout은 바꾸지 않는다.
- AI 수준 평가의 호출 예산은 100초다. 모든 모드 전환·Core 재요청이 같은 deadline을 공유하고 SDK 자동 재시도는 0으로 설정한다. 각 호출에 남은 시간을 timeout으로 전달하고 호출 전후 deadline을 검사한다. 네트워크 timeout은 외부 모델 실행·과금 취소를 보장하지 않는다.
- dispatch 거절·LLM 실패·기한 초과는 가능한 경우 `COMPLETED + FALLBACK + NOT_APPLIED`로 확정한다. 현재 속마음 조회처럼 만료 정리는 GET에서 조건부 수행할 수 있지만 **LLM 생성은 하지 않는다.** 따라서 DB까지 완전한 read-only GET이라고 문서화하지 않는다.
- 비동기 작업 완료와 만료 정리는 같은 잠금·상태 조건·유일성 규칙을 사용한다. GET이 여러 번 실행되거나 늦은 결과가 돌아와도 승급·fallback 저장은 한 번이다.
- DB 자체가 불가하면 저장된 fallback을 항상 반환할 수는 없다. 가능한 경우 FAILED를 기록하고, DB 접근도 불가하면 재시도 가능한 HTTP 오류를 반환한다. FE는 안내·다시 조회를 제공하며 임의 측정 점수를 만들지 않는다.

### 6. JSON 출력 방식 전환과 평가 fallback의 구분

```text
strict json_schema
  └─ 명시적인 해당 기능 미지원 → json_object
       └─ 명시적인 해당 기능 미지원 → 프롬프트 JSON + 직접 파싱
각 응답 → JSON 파싱 → Pydantic Core 검증 → ID·원문 근거·비즈니스 검증
  ├─ Core 유효 → Details만 선택 검증 → BE 계산·저장
  └─ Core 무효 → Core만 1회 재요청 → 다시 무효면 BE FALLBACK
```

- 출력 방식 전환은 평가 기준을 낮추는 일이 아니다. 세 방식 모두 동일한 서버 검증을 통과해야 MODEL로 저장한다.
- 별도 이슈는 미지원 오류 분류, 응답 모드 협상, JSON 파싱을 담당한다. LAN-438은 평가 스키마·Core/Details 격리·원문 검증·Core 1회 재요청·BE fallback을 담당한다.
- 400/404라는 상태 코드만으로 전환하지 않는다. `response_format` 또는 해당 strict 기능의 미지원임이 확인되는 구조화 오류/검증된 메시지만 허용한다. 잘못 만든 JSON Schema, 인증·권한, quota, 429, 일반 5xx·timeout·빈 응답·안전 거절은 모드 미지원과 분리한다.
- JSON 형식이나 근거가 틀렸다는 이유로 json_object/프롬프트 모드로 내려가지 않는다. 이는 Core 복구 경로이며, Details만 틀리면 재호출하지 않는다.
- 같은 논리 평가에서 모드는 한 방향으로만 이동하고 Core 재요청도 마지막 선택 모드를 이어받는다. 최대 2회의 미지원 전환과 최초 생성·Core 재요청으로, SDK 자동 재시도를 제외한 최대 4회 provider 요청을 상한으로 잡는다. 공통 helper의 지원 범위를 먼저 확인하고 루프를 중첩하지 않는다.
- 전송/인증/예산 실패는 BE fallback으로 연결하며 별도 무제한 재시도를 추가하지 않는다. 성공한 fallback 표시값은 실제 관찰 점수가 아니며 프로필 변경·학습용 유효 평가에 포함하지 않는다.
- 모드, 전환 사유 코드, Core 재요청 횟수, 최종 source, 지연·토큰·비용을 기록한다. API key, raw prompt, 사용자 답변 전문은 운영 로그에 남기지 않는다.

### 7. FE 인계

FE 구현은 이 PR의 범위 밖이며 아래 항목을 후속 호환성 작업으로 추적한다. 완료 전에는 수준 결과 표시·결제 흐름까지 구현됐다고 판단하지 않는다.

- [ ] 기존 피드백 DTO는 유지하고 신규 수준 평가 GET DTO와 폴링을 연결한다.
- [ ] 5개 영역 게이지·설명, FALLBACK 안내, FAILED 재조회 화면을 연결한다.
- [ ] 결과 확정 후 프로필·표현 캐시를 갱신하고 결제 전환 E2E를 검증한다.

- 마지막 발화의 기존 세션 완료 정보를 기준으로 피드백 POST와 수준 평가 GET을 병행한다. 피드백 응답에서 평가 상태·결과를 읽지 않는다. 신규 GET이 PREPARING이면 약 2초 간격으로 조회하며 요청이 겹치지 않게 한다.
- 피드백을 읽는 도중 완료돼도 화면을 강제로 전환하지 않는다. 피드백 마지막 단계에서 준비된 평가를 표시한다.
- 마지막 단계까지 PREPARING이면 분석 중 화면을 사용한다. 임의 타이머 만료를 평가 실패나 Level 3 판정으로 처리하지 않는다.
- COMPLETED/FAILED 또는 화면 이탈 시 폴링을 멈춘다. 복귀 시 GET으로 재개하며, 새 평가 생성 요청을 보내지 않는다. 네트워크 오류는 제한된 재조회·안내로 처리한다.
- COMPLETED 응답 이후 사용자 프로필/표현 쿼리 캐시를 갱신하고 `GET /api/v1/expressions/1`을 조회한다. 요약만 끝난 시점의 옛 수준으로 표현 학습을 확정하지 않는다.
- FALLBACK/근거 부족에는 기존 예비 결과 표시 계약을 적용한다. 수준 미설정 fallback의 표현 난이도는 현행 기본값을 유지하며 새 정책을 몰래 추가하지 않는다.
