# LAN-438 공통 온보딩 진단 4문항

## 확정 계약

- 시나리오 1 신규 시작은 사용자 수준 미설정 또는 1~5 모두 같은 4문항이다.
- 질문과 번역 원문은 onboarding-questions.json을 기준으로 한다.
- 질문 묶음 DIAGNOSTIC은 사용자 수준이 아니다. 최초 수준 평가는 1~5 전체 범위다.
- 신규 시작과 목록·일일·관리자 미리보기는 공통 진단 묶음을 사용한다.
- 과거 세션은 저장된 질문 그룹과 3문항 구성을 유지한다. 기존 질문·번역·메타데이터·음원을 덮어쓰거나 비활성화하지 않는다.
- 4문항의 실제 답변 모두 평가하며 기존 Core/Details, 충분성, 초기화·승급·Fallback 계약을 유지한다.
- 사용자 수준 선택 화면 삭제는 FE 작업이다. 기존 사용자 설정 API 삭제는 포함하지 않는다.

## 구현과 검증

- 공통 그룹 CHECK 제약 추가, 신규 시작과 미리보기 조회 변경.
- 기존 세션 후속 질문과 평가 메타데이터는 저장된 그룹으로 조회.
- 수준 미설정 및 1~5 각각 4문항 진행·마지막 턴 완료·평가 입력 4건 통합 테스트.
- 진단 그룹의 Level 1~5 평가 범위 및 기존 그룹 질문 보존 회귀 테스트.
- 독립 검수에서 기존 그룹 덮어쓰기 위험을 발견해 별도 DIAGNOSTIC 그룹으로 보완.
- 최종 `./gradlew spotlessApply check` 통과. 실제 V87 SQL 실행, 수준 미설정·1~5의 공통 질문 진행, 기존 세션 질문 수 3 보존을 검증했다.
- V86/V87, 질문·번역·메타데이터·음원 URL까지 포함한 독립 재검수에서 추가 blocker 없음.

### 블라인드 기준표 작성

1. 작성과 분리된 새 컨텍스트에서 기준 평가를 수행한다. 입력은 공통 질문·답변과 고정 루브릭뿐이며, 작성 목표 수준과 제품 평가 결과를 보여주지 않는다.
2. 기준표에는 질문별 5개 영역의 수준 또는 미관찰 상태, 원문 근거, 세션별 허용 수준 범위, 수준 확정 가능 여부를 기록한다. 자료만으로 판단할 수 없는 항목은 억지 정답을 만들지 않는다.
3. 가능하면 제품 평가 모델과 다른 모델로 기준표를 만든다. 사람 검수 전에는 model_reference라는 출처를 명시하고, 정확도가 아닌 기준 평가와의 일치도로 보고한다. 기존 사용자 자가선택 수준도 정답으로 취급하지 않는다.
4. 입력 파일과 기준표를 별도 파일로 저장하고 해시·분할을 봉인한다. 실행기는 입력만 읽고, 결과 생성이 끝난 뒤 별도 채점기가 기준표와 결합한다.
5. 질문별 기준표를 실제 BE 계산에 넣어 정책 기대값도 만든다. 독립 세션 수준 판단과 BE 정책 기대값은 분리해, LLM 판정 오차와 가중 계산·충분성 정책의 한계를 구분한다.

### 실제 실행 순서

1. 로컬 API와 격리 DB를 준비하고 2개 대화로 연결만 점검한다. 사용자 learningLevel=null, promotionStreak=0이며 시나리오 진행 가능 상태여야 한다. 관리자 세션도 진행도를 쓰므로 반복마다 독립 사용자를 쓴다.
2. 실제 BE 경로로 시나리오 1 세션 시작 → TEXT 답변 4회 제출 → 턴별 피드백 준비 → 세션 피드백 POST → DB·프로필 확인 → 표현 GET을 실행한다. API 계약의 실제 DTO와 기존 ScenarioSessionApiIntegrationTests를 재사용한다.
3. AI의 session-feedback은 같은 프로세스에 쌓인 message-feedback 캐시와 원문 일치 검사가 필요하다. 단일 AI 프로세스에서 정상 턴 처리를 완료하고, 최종 평가만 단독 호출하거나 캐시를 가짜 값으로 채우지 않는다. API가 반환한 실제 질문·ID·완료 상태를 사용한다.
4. 40개 대화를 각각 1회 실행한다. 반복성 표본은 출력 확인 전에 기본 대화 중 수준별 2개씩 10개를 고정하고, 각 2회 추가 실행한다. 총 60개 신규 세션이다. 반복은 새 사용자·세션으로 전체 대화를 다시 수행한다.
5. 최초 2개 연결 점검에서 endpoint별 호출 수·재시도·토큰·비용·시간을 기록하고 전체 비용을 추정한다. 세션 평가 60회가 전체 LLM 호출 60회를 뜻하지 않는다. 상한 없는 재시도는 하지 않으며 테스트 실패도 결과로 보존한다.
6. 봉인 검증용 데이터 실행 중 기준표·평가 로직을 수정하지 않는다. 실패 원인을 관찰/근거 검증/JSON 복구/충분성/수준 적용/표현 조회로 분류한다. 개선 실험은 baseline 이후 별도 run과 신규 holdout으로 수행한다.

### 필수 관찰과 오류 테스트

- DIAGNOSTIC 4문항, 4번째 답변에서 완료, AI 평가 입력 4개, 저장된 Core의 ID·원문 근거 일치를 확인한다.
- 응답 source, 각 영역 score/confidence/observedCount, sufficientEvidence, assessedLevel, displayLevel, changeType, previous/appliedLevel 및 프로필 실제 값을 기록한다. displayLevel의 기본값을 평가 성공으로 세지 않는다.
- 각 영역의 요구도 총합은 3.4다. MEDIUM 1개 미관찰이면 2.7/3.4≈0.79, HIGH 1개 미관찰이면 2.4/3.4≈0.71이다. 해당 영역 외에는 동일한 fixture로 충분성 통과·실패 차이를 확인한다.
- 5개 영역 모두 충분해야 INITIALIZED다. 짧은 적절한 답변이 불필요하게 미관찰로 처리되는지, 상호작용·화용 근거 부족으로 대부분 NOT_APPLIED가 되는지 별도로 집계한다.
- 실제 4문항에서 Level 5의 상황 수행·화용 근거를 관찰할 기회가 있는지 확인한다. 고급 기준 대화가 낮게 나와도 즉시 모델 오답으로 단정하지 않고 질문 관찰 기회와 루브릭의 한계를 함께 분석한다.
- 모델 응답 토큰 제한은 현재 평가 포함 시 2048이다. 응답 잘림·형식 오류·Core 유실을 따로 기록한다. 이를 테스트 도중 임의로 늘리지 않는다.
- 오류 주입은 별도 로컬 stub 회귀 검사로 수행한다: Details만 오류, Core 오류, timeout, AI 5xx, 캐시 원문 불일치. 실제 네트워크 품질 결과와 합산하지 않는다.
- 오류에도 BE 결과 응답이 유지되는지, 무효 평가가 프로필·streak를 바꾸지 않는지, 같은 세션 피드백 재요청이 평가 행·수준 변경을 중복 생성하지 않는지 확인한다. AI의 직접 응답은 오류일 수 있으므로 항상 응답 계약은 BE에서 검증한다.
- 피드백 응답 완료 후 GET /api/v1/expressions/1을 호출해 현재 적용 수준의 난이도와 일치하는지 확인한다. 진단 실패 시 미설정 프로필은 유지되고 기존 기본 난이도 4~5가 나오는 현행 동작은 미결 정책으로 보고한다.

| 정상 기준 대화의 최초 수준 확정 | 기준 평가가 확정 가능하다고 판정한 대화 중 90% 이상. 성공/전체 n을 함께 표시한다. |
| 기준 수준 일치 | 확정 가능 대화에서 허용 범위 내 80% 이상, 범위로부터 1단계 이내 95% 이상. 미확정은 실패로 포함하고 확정 건만의 일치율도 별도 제공한다. |
| 반복성 | 반복 표본 10개에서 3회 assessedLevel 범위가 1 이하이고 INITIALIZED 여부가 동일. 미확정 횟수도 표시한다. |
| 영역 평가 | 5개 영역별 차이·미관찰율·판정자 불일치를 보고한다. 종합 점수 하나로 숨기지 않는다. |
| 데이터·적용 불변조건 | 잘못된 근거 수용, invalid/Fallback의 프로필 변경, 중복 평가·수준 변경 0건. 오류 주입 시 BE 응답 100%. |
| 운영 참고값 | 실제 호출 기준 형식 오류율·Fallback율·토큰·비용·p50/p95 지연. 표본 수와 재시도 포함 여부를 명시한다. |

- 봉인 검증용 20개 결과를 주 결과로 보고하고 개발용·경계·반복·오류 주입 결과는 각각 분리한다. 모든 비율에 분모를 적는다.
- 결과물: 익명 입력, 별도 기준표, 실행 manifest(HEAD·모델·설정·해시), 세션별 결과 JSONL, 요약 보고서, 실패 사례별 원문과 판단 근거.
- 합성 데이터만 저장하며 시크릿·인증 헤더를 결과에 포함하지 않는다. 결과 디렉터리는 실행 시 별도로 정하고 대용량 원시 산출물은 자동 커밋하지 않는다.
- 최종 보고서는 수준 구분 가능 여부, 초기화 차단 비율, 가장 큰 실패 원인 3개, 수정이 필요한 최소 범위, 사람/실사용자 검증이 남은 항목을 명시한다.
