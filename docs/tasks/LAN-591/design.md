# LAN-591 앱 설치별 푸시 소유권

## 결정

- 중복 방지 단위는 앱 설치 UUID다. 한 설치에는 현재 로그인한 계정과 활성 Expo Token을 최대 하나만 연결한다. 다른 설치는 독립적으로 수신한다.
- Expo Token은 교체될 수 있으므로 설치 식별자로 사용하지 않는다. 기존 `user_push_token`의 `installation_id`를 nullable로 추가해 이전 앱의 Token 행을 유지한다.
- 활성 설치 등록 시 현재 인증 계정의 설치 ID 없는 활성 Token을 같은 트랜잭션에서 정리하고, 현재 Token만 해당 설치에 연결해 활성화한다. 다른 계정의 구형 Token과 설치 ID가 연결된 다른 기기는 유지한다. 비활성 요청은 구형 Token 정리를 실행하지 않는다.
- 계정 전환 시 새 계정으로 설치를 재연결한다. `pushEnabled=false`로 전환해도 이전 계정의 Token을 비활성화한다.
- 발송 이력 선점 시 Token의 `ACTIVE` 상태와 계정 소유권을 다시 검사한다. 푸시 `data.userProfileId`는 앱이 탭 시점에 현재 계정과 비교한다. 서로 다르면 해당 딥링크를 열지 않는다.
- 기기 OS 권한과 계정별 서버 푸시 동의 상태는 별개다. 현재 동작과 같이 활성 Token을 등록하면 해당 계정의 서버 푸시 동의를 `GRANTED`로 기록한다.

## FE 연동 계약

`PUT /api/v1/me/push-devices/{installationId}`는 인증이 필요하다. 앱 실행 시 로컬에 저장된 설치 UUID를 사용하고, 없으면 한 번 생성해 보관한다. 로그인, 계정 전환, OS 알림 권한 변경, Expo Token 변경 때 현재 계정으로 동기화한다. 서버는 설치 UUID가 이미 있으면 그 연결을 갱신하고, 없으면 같은 Expo Token의 기존 행을 연결하거나 새 행을 만든다. 활성 등록마다 같은 계정의 설치 ID 없는 다른 활성 Token을 비활성화한다. 구형 API가 Token을 다시 활성화하더라도 다음 설치 API 동기화에서 정리한다.

```json
{"platform":"IOS","expoPushToken":"ExpoPushToken[...]","pushEnabled":true}
```

`pushEnabled=true`이면 올바른 Expo Token이 필수다. `false`이면 Token은 생략할 수 있다. 앱이 로그아웃할 때는 `POST /api/v1/auth/logout`의 기존 `refreshToken`과 함께 `installationId`를 전달한다. 유효한 Refresh Token의 계정이 여전히 설치를 소유할 때만 설치 푸시가 비활성화된다.

일반 계정 대상 Push의 `data`에는 기존 `url`과 함께 `userProfileId`가 들어간다. 앱은 알림을 열 때 현재 로그인 계정과 이 값을 비교하고, 일치하지 않으면 계정 전환 안내나 안전한 기본 화면으로 이동해야 한다. 일치해도 시나리오·표현 접근 권한을 확인한다.

## 배포와 한계

- 설치 ID 마이그레이션은 `V129__add_push_installation_id.sql`이다. PR #224의 V126, PR #226이 선행 조건으로 명시한 V127 및 해당 PR의 V128과 번호가 겹치지 않도록 배정했다. 병합·배포 전 번호와 적용 순서를 다시 확인한다.

- 기존 `PUT /api/v1/me/expo-push-token`은 이전 앱과의 호환성을 위해 유지한다. 신규 앱은 설치 API만 사용한다.
- 어떤 설치도 새 API로 활성 등록하지 않은 계정의 기존 Token은 계속 발송 대상이다. 해당 계정에서 새 API로 활성 등록하면 현재 Token을 설치에 연결하고, 같은 계정의 설치 ID 없는 다른 활성 Token은 비활성화한다. 서비스 전체의 일괄 정리는 하지 않는다.
- 같은 계정의 아직 전환하지 않은 다른 기기도 비활성화될 수 있다. 해당 기기가 새 FE로 설치 API에 등록하면 다시 수신한다. 같은 휴대폰의 과거 Token과 다른 기기의 Token을 기존 데이터로 구분할 수 없어 승인한 전환 정책이다. 이미 설치 ID가 연결된 다른 기기는 영향을 받지 않는다.
- 동일 설치에서 발급됐더라도 값이 다른 과거 Token은 서버가 같은 설치임을 확인할 수 없다. 다른 계정에 남은 그런 Token은 해당 값이 무효화되거나 별도로 식별될 때까지 중복을 일으킬 수 있다. 같은 계정에 누적된 구형 Token은 이번 정리 대상이지만, 다른 계정에 남은 구형 Token까지 최초 접속만으로 정리한다고 보장하지 않는다.
- Token 소유권은 발송 이력을 선점할 때 확인하지만, 선점 후 Expo에 요청하기 전 계정이 바뀔 수 있다. 이미 전달된 알림도 회수할 수 없으므로 탭 시점의 FE 계정 검사가 필요하다.
- Expo 전송 자체는 드물게 중복 전달될 수 있어, 서버의 한 설치당 한 발송 후보 정책이 OS 표시 건수의 절대 보장은 아니다.

## 추가 검증

- 같은 계정의 기존 Token 두 개 중 현재 Token은 연결하고 다른 Token은 비활성화한다.
- 설치 ID가 연결된 다른 기기와 다른 계정의 구형 Token은 유지한다.
- 현재 Token이 신규 값인 경우에도 구형 Token을 정리하며, 반복 등록 결과는 동일하다.
- 비활성화된 다른 기기가 설치 API로 등록하면 수신을 재개한다.
- `pushEnabled=false` 요청은 해당 설치만 비활성화하고 구형 Token은 유지한다.
- 설치 등록이 실패하면 구형 Token 정리와 신규 Token 등록을 함께 롤백한다.
- 검증 결과: `./gradlew spotlessApply check --offline` 통과. 전체 1,801건 중 실패·오류 0건, 생략 12건. Push Token API 통합 테스트 17건 통과.
- BE 로컬 검증이며 FE 연동, 운영 배포, 실제 기기 수신은 별도 확인이 필요하다.

## 독립 리뷰 반영

- 설치 동기화·구형 Token 등록은 로그아웃과 동일하게 프로필을 먼저 잠근다. 프로필과 Token의 잠금 순서 역전으로 한 요청이 실패할 수 있는 문제를 수정했다.
- 설치·일치 Expo Token·구형 정리 대상을 한 쿼리로 ID 오름차순 잠금한다. 배치 발송과 구형 Token 정리 사이의 잠금 순서도 통일했다.
- 독립 리뷰에서 발견한 두 결함을 수정 후 재검토했으며 추가 확정 결함은 없었다. 프로필 잠금 실패 시 Token 미선점 3건과 실제 저장소 조회 순서 1건을 회귀 테스트로 추가했다. PostgreSQL 동시 실행 재현은 수행하지 않았다.
- 리뷰 반영 후 `./gradlew check --offline` 통과. 전체 1,805건 중 실패·오류 0건, 생략 12건.
