# LAN-461 사용자 일일 알람 설정

## 범위와 결정

- 사용자당 알람 1개를 매일 반복한다. 이 범위는 사용자 답변으로 확인했다.
- 서버는 설정 조회·저장·수정만 담당한다. 실제 예약·취소·재예약·전면 표시는 클라이언트가 담당한다.
- 시각은 기기 현지 시간의 `HH:mm`으로 해석한다. 서버는 UTC 변환이나 다음 실행 시각 계산을 하지 않는다.
- 기본 상태는 `time: null`, `enabled: false`다. 조회만으로 설정 행을 생성하지 않는다.
- `enabled`는 사용자의 알람 설정이며 푸시 동의, OS 권한, 실제 기기 예약 성공 상태와 별개다.
- `user_alarm`의 PK를 `user_profile_id`로 두어 사용자당 1개를 보장한다. 프로필의 다른 설정 갱신이 알람을 덮어쓰지 않도록 별도 테이블에 저장한다.
- 최초 등록·수정은 기존 활성 사용자 프로필 잠금을 사용해 직렬화한다. 동일 사용자의 동시 요청은 나중에 처리된 요청의 전체 설정으로 남는다.

## API 계약

두 API 모두 인증된 본인의 설정에만 접근한다. 사용자 ID를 입력받지 않는다.

| 메서드와 경로 | 동작 |
| --- | --- |
| `GET /api/v1/me/alarm` | 저장된 알람 설정 조회. 미설정 사용자도 200을 반환한다. |
| `PUT /api/v1/me/alarm` | 알람 설정 전체 등록·변경. 같은 요청을 반복해도 알람은 1개다. |

PUT 요청과 성공 응답의 `data`는 다음 구조다.

```json
{"time": "07:30", "enabled": true}
```

- `time`과 `enabled`는 PUT에서 모두 필수다. 시각은 `00:00`~`23:59`만 허용하며 초·시간대·공백을 받지 않는다.
- 끌 때는 기존 시각과 `enabled: false`를 보낸다. 다시 켤 때 저장된 시각을 사용할 수 있다.
- 잘못된 입력은 `400 / VALIDATION_FAILED`, 미인증 또는 탈퇴 계정은 401이다.
- 성공 응답은 설정 저장 완료만 의미한다. 서버에서는 SQS, Expo Push, EventBridge 예약을 생성하지 않는다.

## 클라이언트 연동

1. 로그인 후 GET으로 설정을 복원한다. 미설정 또는 비활성 상태면 로컬 예약을 생성하지 않는다.
2. 사용자가 시각이나 활성 상태를 바꾸면 PUT으로 전체 설정을 저장한다.
3. 저장된 설정에 맞춰 기존 예약을 취소하고, 활성 상태면 매일 같은 현지 시각으로 예약한다. 연속 변경 요청과 로컬 예약 적용 순서도 클라이언트에서 직렬화한다.
4. OS 권한 부족이나 예약 실패는 클라이언트가 표시하고 재시도한다. 서버 저장과 기기 예약은 하나의 원자적 작업이 아니므로 앱 재진입 시 GET 결과와 실제 예약을 다시 맞춘다.
5. 로그아웃·탈퇴·계정 전환 때 해당 계정의 로컬 예약을 취소한다. 시간대 변경과 기기 재시작 뒤 예약 복구도 클라이언트가 처리한다.

설정은 계정 단위다. 다른 기기의 기존 예약을 서버가 즉시 취소하거나 동기화하지는 않는다. 다른 기기는 앱 재진입 시 저장된 설정을 반영한다.

## 검증 결과

- `./gradlew spotlessApply check` 통과. 전체 968개 중 964개 성공, 환경 조건에 따른 기존 PostgreSQL 테스트 4개 건너뜀.
- 알람 API 통합 테스트 7개 통과. 기본 상태, 등록·수정·비활성화·재활성화, 잘못된 입력, 사용자 격리, 미인증·탈퇴 계정, 동시 최초 등록, OpenAPI의 null 시각 타입을 확인했다.
- H2에서 전체 Flyway 마이그레이션과 JPA 스키마 검증을 실행했다.
- 격리된 로컬 PostgreSQL 15.18에서 V85 파일을 실행하고 시각 저장·수정, PK·FK·NOT NULL 제약을 확인했다. 기존 운영 스키마 전체에 대한 마이그레이션 검증은 아니다.
- 독립 리뷰에서 지적한 OpenAPI null 타입을 수정하고 재검토를 완료했다. 추가 blocker는 없었다.
- 운영 DB 적용, 서버 배포, 실제 기기 예약·전면 표시는 이 작업에서 검증하지 않았다.
