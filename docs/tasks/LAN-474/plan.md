- 새 진단 그룹은 읽기만 지원하고 기존 시나리오 1의 3문항을 유지한다. 결제·수준 평가·스몰톡 제한은 포함하지 않는다.
- 기존 비동기 메시지 피드백에 DB 작업 기록과 선택적 완성 결과를 추가한다. 최종 피드백의 캐시 누락은 서버에서 복구 후 한 번 재요청한다. 외부 호출·대기 중 DB 트랜잭션을 유지하지 않는다.
- 복구 및 최종 호출은 기존 최종 피드백 제한 시간 안에서 수행하며 실패를 가짜 평가 결과로 저장하지 않는다.
- `R__ensure_message_feedback_work.sql`은 피드백 작업 테이블이 없을 때만 생성한다. main V81과 develop V97 사이에 낮은 버전 번호를 끼워 넣지 않는다. 2차 작업 브랜치의 미배포 V100도 같은 테이블을 중복 생성하지 않게 조정한다. 이후 스키마 변경은 버전 마이그레이션으로 관리한다.

- [x] HTTP 회귀, 동시 복구, 제한 시간, 구·신 AI 계약 검증.

## 검증 결과.

- `./gradlew spotlessApply check` 성공. 904개 중 903개 성공, 외부 AI 계약 테스트 1개 조건부 제외. 깨끗한 빌드에서도 본 테스트들을 검증했다.
- `LAN474_AI_URL=http://127.0.0.1:7814 LAN474_EXPECT_SNAPSHOT=true ./gradlew test --tests '*AiDeploymentCompatibilityIntegrationTest'` 성공. 실제 새 AI 66dc226 라우터와 hotfix RemoteAiConversationClient를 연결했다.
- 같은 테스트를 origin/main AI 86c1888에 7815 포트와 `LAN474_EXPECT_SNAPSHOT=false`로 실행해 성공했다. 외부 LLM만 대역이다.
- 구 BE가 읽지 못하던 진단 세션의 4문항과 기존 세션의 3문항을 각각 실제 BE HTTP 요청으로 확인했다.
- 원본 작업 기록이 없는 구 세션 복구, DB 결과로 새 AI 캐시 유실 극복, 구 AI가 완성 결과를 무시할 때 캐시 재생성, 작업 임대·동시 실행·삭제 경합·복구 제한 시간·서버 종료를 검증했다.
- 기존 테스트 정리 중 결과 저장과 메시지 삭제의 역순 잠금이 재현되어, 부모 메시지 → 작업 순서로 맞추고 늦은 결과를 폐기하는 회귀를 추가했다.
- 실제 Flyway로 반복 초기화 후 후속 버전 적용을 검증했고 저장 결과와 버전 순서를 유지했다. hotfix 초기화 SQL과 2차 작업 브랜치의 조정된 V100 SQL은 동일하다.
- 사용자 요청에 따라 주 에이전트가 직접 소스와 호출 경계를 검토했다. 독립 리뷰, 실제 ECS 교체, PostgreSQL 운영 DB, FE 실기기 검증은 수행하지 않았다.

## 배포 조건.

1. 이 hotfix를 모든 운영 BE에 반영하고 구 AI와의 실제 정상 흐름을 확인한다.
2. 2차 릴리즈에는 이 hotfix의 복구·잠금 순서 수정과 V100 중복 생성 방지를 함께 반영한다. 현재 2차 작업 브랜치에는 V100 조정만 있으며 전체 hotfix 반영은 별도다.
3. 결제와 AI 내부 인증 강제는 기존 출시 계획대로 별도 활성화한다.

구 AI는 인스턴스별 메모리를 사용한다. 복구 요청과 최종 요청이 서로 다른 구 AI로 분산되는 상황까지 무오류를 보장하지 않는다. 장기 LLM 장애나 전체 요청 제한 시간 초과는 기존 실패 응답으로 남기며 가짜 점수로 성공 처리하지 않는다.
