# LAN-558 Sentry 진단 정보 개선

## 승인된 범위

- 사용자 요청: Sentry에서 자세한 예외 사항을 확인할 수 있게 BE와 AI 관측 경로를 개선한다.
- 민감정보 제거, 최종 실패/정상 복구 분류, API 응답과 fallback 동작은 유지한다.
- 예외 타입과 원인 스택, 허용된 검증 사유/필드, 외부 HTTP 상태를 남긴다.
- 프리톡 교정 코드 오류 누락, 일반 BE 로그의 그룹화 충돌, 요청 ID 전파를 보완한다.
- 추가 사용자 요청: 인증된 내부 사용자 ID를 MDC와 Sentry `user.id`에 연결하고 AI까지 전달한다.
- 모델 응답 원문, 발화, 프롬프트, 인증 정보는 수집하지 않는다.

## 구현과 검증

1. AI 공통 진단 필터와 수준 평가/교정/속마음 실패 원인 보존.
2. BE 공통 이벤트 정보, 외부 AI HTTP 오류, 알림/첨부 정리 보고 경로 보완.
3. SDK 메모리 전송으로 상세 정보 보존과 민감정보 제외를 함께 검증.
4. AI 전체 unittest와 BE `./gradlew check` 실행 후 저장소별 커밋.

## 변경 내용

- Sentry 제목과 최상위 예외 메시지에 기능/단계/고정 사유를 표시한다. 원인 타입과 스택은 유지하고 원문·본문·로컬 변수는 제외한다.
- 공통 AI 클라이언트와 시나리오 AI 클라이언트가 HTTP 실패 상태를 `AiUpstreamException`에 보존한다. 공개 오류 코드는 유지하고 정상 400/409 거절에는 원인을 추가하지 않아 기존 보고 분류를 유지한다.
- `error_code`와 `upstream_status`를 원인 정제 전에 추출하고 일반 SDK 직접 보고에도 적용한다. 보고 후 MDC는 원래 값으로 복원한다.
- 일반 오류 로그의 기본 그룹화 지문에 logger를 포함한다. 알림 예약/편지 답장 큐/정기 알림/첨부 정리 경로는 명시적인 기능·단계·원인 예외를 보고한다.
- AI 구현과 상세 이벤트 예시는 landit-ai의 `docs/tasks/LAN-558/plan.md`에 기록했다.
- access token과 활성 사용자 검증이 끝난 뒤에만 `user_id`를 MDC에 설정한다. 호출자가 보낸 사용자 ID 헤더는 신뢰하지 않으며, 요청 종료/예외 시 기존 컨텍스트를 복원한다.
- Sentry에는 양의 Long 내부 ID만 `user.id`로 보존한다. 이메일·이름·IP·토큰 등 기존 scope 사용자 정보는 제외한다. Logback 비동기 처리에는 로그 생성 당시 ID를 사용한다.
- 공용 비동기 실행기와 프리톡 요약 전용 실행기에 요청/사용자 ID를 전파하고 작업 종료 시 복원한다. 사용자 요청과 관계없는 정기 작업에는 사용자 ID를 임의로 부여하지 않는다.
- AI 내부 인증 토큰이 설정된 요청에만 `X-Landit-User-Id`를 전송한다. AI도 내부 인증 성공 후에만 이 ID를 허용한다. 두 서비스의 내부 토큰 설정이 필요하며 API 본문과 DB 스키마는 변경하지 않는다.

## 검증 결과

- `./gradlew spotlessApply check` 통과. 228개 테스트 클래스, 1,783개 중 1,771개 통과, 12개 기존 조건부 제외, 실패/오류 0개.
- SDK 메모리 전송으로 원인 스택, HTTP 상태/오류 코드 보존, 민감정보 제외, MDC 복원, 태그 없는 다른 logger의 그룹 분리를 확인했다.
- 로컬 HTTP 서버로 두 AI 클라이언트의 401/429/500/503 원인 상태 보존과 기존 공개 오류 코드 유지를 검증했다. 기존 400/409 거절은 cause가 없음을 확인했다.
- 기존 정상 복구/중복 억제, 알림/피드백 테스트를 포함한 전체 검사가 통과했다.
- 추가 12개 테스트로 인증 전후 MDC 격리, 비동기 작업과 프리톡 요약 ID 전파/복원, AI 내부 인증 설정별 헤더 처리, SDK 직접 보고 및 Logback 스냅샷의 사용자 ID 보존과 PII 제외를 검증했다.
- 운영 Sentry 전송, 배포, 실제 provider 호출은 수행하지 않았다. 변경은 배포 후 새로 발생하는 이벤트부터 적용되며 과거 이벤트의 제거된 상세 정보는 복원하지 못한다.

## 추가 MDC 확장 계획 재검토

2026-09-24 사용자 요청에 따른 계획 검토 결과다. 위의 예외 진단과 사용자 ID는 구현 완료 상태이고, 이 절의 추가 항목은 아직 구현하지 않았다. BE와 AI의 추가 확장 계약은 이 절을 기준으로 한다.

### 코드에서 확인한 보완점

1. `session_id` 하나로 통일하면 안 된다. 시나리오 수준 평가의 `LoadedSessionFeedbackContext.sessionId`는 `learning_session.id`이고, 프리톡 `FreeTalkMessageService`와 교정 복구가 AI에 보내는 `sessionId`는 `free_talk_session.id`다. DTO 이름이나 Javadoc만 보고 식별자의 의미를 추정하지 않는다.
2. `RequestObservationFilter`는 실행 순서가 지정되지 않았다. 인증에서 종료되는 요청도 요청 ID를 갖도록 Security 필터보다 앞에서 요청 문맥을 열어야 한다. 반면 라우트 패턴은 MVC가 핸들러를 선택한 다음에 확정해야 한다.
3. `FailureObservation.afterCommit`은 현재 실행 시점의 MDC를 읽는다. 새 작업 scope가 트랜잭션 완료 전에 닫힐 수 있으므로 등록 당시의 허용된 문맥을 저장하고 콜백에서 복원해야 한다.
4. AI는 생성·검토·교정·임베딩에 서로 다른 모델을 사용할 수 있다. 프리톡 API의 오류 로그는 현재 기본 `openrouter_model`을 읽기도 하므로 이를 오류 모델의 근거로 사용하지 않는다. 최종 오류에 연결된 호출의 모델을 보존해야 한다.
5. 정기 복구 작업에는 HTTP 요청이 없다. 빈 MDC를 그대로 전달하는 것으로는 대상 세션/메시지를 추적할 수 없으므로 작업마다 신뢰할 수 있는 DB 조회 결과로 문맥을 새로 구성해야 한다.

### 1차 적용 범위와 값의 의미

| 필드 | 값의 출처와 범위 | Sentry 기록 |
| --- | --- | --- |
| `request_id`, `user_id` | 기존 서버 요청 ID와 인증 사용자 ID를 유지한다. | 요청 ID 태그와 `user.id`를 유지한다. |
| `learning_session_id` | BE 소유권 검증을 거친 학습 세션 ID. AI 시나리오 요청의 검증된 `sessionId`도 이 의미다. | 검색 태그. |
| `free_talk_session_id` | BE가 실제 조회한 프리톡 세션 ID. AI 프리톡 요청에서 이 의미가 확인된 `sessionId`만 매핑한다. | 검색 태그. |
| `message_id` | 현재 작업 대상인 저장된 메시지 ID. API별 `messageId`/`submittedMessageId`를 명시적으로 매핑하고 이력의 마지막 메시지로 추정하지 않는다. | 검색 태그. |
| `http_method`, `http_route` | 해당 서비스의 요청 메서드와 프레임워크가 확정한 경로 패턴. 예: `/api/v1/sessions/{sessionId}/messages`. | 검색 태그. |
| `provider`, `model` | AI 호출 직전에 결정한 공급자 설정과 요청 모델. `provider=openrouter`는 게이트웨이를 뜻하며 실제 하위 추론 업체를 추정하지 않는다. | AI 오류의 검색 태그. BE에는 알 수 없는 모델을 채우지 않는다. |

- BE 프리톡 작업에서 두 종류의 세션 ID를 이미 알고 있다면 둘 다 남긴다. AI가 프리톡 세션 ID만 아는 경우 학습 세션 ID를 만들거나 같은 숫자를 복사하지 않는다.
- AI는 내부 인증에 성공한 요청의 검증된 DTO에서 명시적으로 ID를 추출한다. ID 없는 API나 DTO 검증 실패에는 ID를 생략한다. 관측 때문에 본문을 다시 읽거나 입력값 전체를 직렬화하지 않는다.
- 세션/메시지 ID는 기존 DTO를 활용한다. 1차에는 이 정보를 위한 새 HTTP 헤더, 공개 API 필드, DB 컬럼을 추가하지 않는다. BE와 AI의 요청 경로는 각각 자기 서비스의 경로로 기록하고 서로 덮어쓰지 않는다.
- 라우트가 확정되지 않은 인증 거절/404는 `http_route=UNKNOWN`으로 기록한다. 원문 경로·쿼리·헤더는 대체값으로 사용하지 않는다. 메서드 역시 알려진 HTTP 메서드만 허용한다.
- `attempt`는 기존 기능별 의미를 유지한다. 업무 작업 재시도와 LLM 검증 재시도, SDK 내부 HTTP 재시도 횟수를 하나로 합치거나 추정하지 않는다.

### 적용 순서

1. 허용 키, 숫자 ID/메서드/라우트/모델 값 검증과 작업 scope를 공통화한다. 모델 식별자는 길이·문자 형식을 제한하고 프롬프트, URL, 시크릿을 복사하지 않는다. scope 종료 시 자신이 변경한 키만 이전 값으로 복원한다.
2. BE 요청 ID/메서드 scope를 Security보다 앞에 두고 MVC 라우트 확정 시 패턴을 보완한다. 오류가 보고되는 시점에 태그가 존재하도록 한다. 종료 후에만 라우트를 채우는 방식은 사용하지 않는다.
3. 시나리오 수준 평가/메시지 피드백과 프리톡 대화·교정·요약·표현·기억 작업에 대상 ID scope를 적용한다. 소유권/대상 조회 후 알고 있는 값만 사용하고 관측 목적으로 추가 DB 조회를 만들지 않는다.
4. 공용 실행기와 프리톡 요약 실행기에는 허용된 요청·작업 문맥만 복사한다. 복구 루프는 항목별로 새 scope를 열어 이전 대상 ID를 지운다. `afterCommit`도 등록 당시 문맥을 저장하고 커밋 후 단일 보고하며 롤백 시 보고하지 않는다.
5. AI 요청 DTO 경계에서 ID를 연결하고 LLM 호출·출력 검증 경계에서 모델 문맥을 보존한다. sync/async/교정 스레드에서 ContextVar를 복원한다. 예외 래핑과 외곽 핸들러에도 실패 당시 문맥을 넘겨 이미 종료된 scope나 나중 호출의 모델로 덮어쓰지 않는다. 발음 판정·임베딩·요약의 별도 호출도 포함한다.
6. BE와 AI Sentry 필터의 허용 목록을 함께 갱신한다. Logback 지연 처리에는 로그 생성 당시 값, SDK 직접 보고에는 캡처 당시 값, 최종 예외에는 보존된 실패 문맥을 적용한다. 요청/사용자/세션/메시지 ID를 메트릭 차원이나 오류 그룹화 지문에 추가하지 않는다.

### 후속 적용으로 분리할 항목

- `job_id`, `job_attempt`는 알림/큐처럼 기존 영속 작업 ID가 있는 경로에 한해 후속 적용한다. 교정 작업의 선점 토큰을 job ID로 사용하거나 관측용 작업 테이블을 만들지 않는다. 학습 복구의 기존 세션/메시지 ID 연결은 1차에 포함한다.
- 사용자 요청이 없는 복구는 조회된 대상 ID로 연결한다. 전역 예약/조회 실패에는 사용자 ID를 임의로 부여하지 않는다. 관리자 요청의 인증 사용자를 작업 대상 사용자로 덮어쓰지 않는다.
- `status_code`, `duration_ms`는 응답 완료 시 확정되는 로그 정보이므로 별도 적용한다. 이미 전송한 예외 이벤트에 최종 HTTP 상태/소요 시간이 자동으로 추가된다고 가정하지 않는다. 전체 HTTP 요청의 새로운 Sentry 이벤트 수집은 추가하지 않는다.
- `release` 연결과 `trace_id`/`span_id` 도입은 배포·분산 추적 설정과 함께 별도 확인한다. 이번 확장에 새 관측 인프라나 배포를 포함하지 않는다.

### 구현 시 검증할 인수 조건

- 서로 다른 두 사용자의 동시 요청, 같은 worker의 연속 작업, 중첩 scope와 예외 종료에서 ID가 섞이지 않는다.
- `learning_session_id=100`과 `free_talk_session_id=7`처럼 서로 다른 값으로 BE/AI 이벤트를 검증한다. 시나리오와 프리톡의 숫자가 같아도 다른 종류의 세션으로 남는다.
- 인증 거절/404/DTO 검증 실패에는 허위 사용자·세션 ID나 원문 URL이 붙지 않는다. 정상 핸들러 안에서 보고한 예외에는 경로 패턴이 이미 들어 있다.
- 요청 종료 후 비동기 실패, 항목이 다른 정기 복구, scope 종료 후 `afterCommit` 보고에도 해당 작업의 문맥이 남는다. 롤백은 최종 실패 이벤트를 만들지 않는다.
- 모델 A 실패 후 B 호출, 생성/검토 모델 변경, SDK 호출 성공 후 출력 검증 실패에서 최종 오류와 관련된 모델만 남는다. 정상 재시도/복구는 기존처럼 Sentry 이벤트를 늘리지 않는다.
- 실제 SDK의 메모리 transport로 최종 이벤트를 확인한다. 새 태그 보존, 원문/PII 제외, ID가 메트릭 차원과 지문에 들어가지 않음을 함께 검증한다.
- BE `./gradlew check`와 AI 전체 unittest를 실행한다. 실제 Sentry 수신 여부는 별도의 배포 후 검증으로 구분한다.

이번 계획 검토에서는 소스 코드를 변경하지 않았다. 기존 통과한 테스트 수는 위의 구현 완료분에 대한 결과이며, 추가 확장의 검증 결과가 아니다.
